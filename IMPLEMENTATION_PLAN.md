# Bicz implementation plan

## Purpose and evidence boundary

Build the public `bicz` tool described by [`DESIGN.md`](DESIGN.md), without representing the current repository as a working product. The repository currently contains an architecture, a deterministic Python ledger benchmark (`economy_benchmark.py`), enforcement contract scenarios (`enforcement_contracts.py`), and a shell runner; it has no installable CLI, daemon, database service, harness adapter, authentication, or release package. The `bicz install`/`bicz status` examples and `bicz/client` import in `DESIGN.md` are illustrative proposals, not commands or an existing package. [`OPENCODE_COMPATIBILITY.md`](OPENCODE_COMPATIBILITY.md) is the pinned OpenCode V1/V2 integration/install contract. [`PRESSURE_MECHANICS.md`](PRESSURE_MECHANICS.md) is the **behavioral design authority** adopted by this plan (livelihood framing, irreversibility, honesty asymmetry, three-class taxonomy, floor/probation/dismissal, pressure protocol); this plan adopts it wholesale and defers mechanism detail to it. `DESIGN.md` was edited only for the first-release wording cutover, and no other repository state was changed.

**One clear statement early: bicz is an incentive-and-accountability tool, not an anti-tamper tool.** It runs same-user and cooperative. It does not contain a same-UID agent, does not isolate the harness, does not sandbox native tools, does not run a privileged service or separate runner principal, and does not use a VM/container boundary. Its protections are (a) **recording** — rewards, losses, and role changes are real operator-recorded ledger events (human at the CLI, who/when/evidence) that change the recorded economy an agent is shown; (b) **integrity evidence** — the ledger is append-only with a hash chain and a periodic external anchor, so tampering is detectable, not preventable; (c) **honest coverage** — every claim about what bicz observes is scoped to what the adapter actually sees, with named unobserved paths. Same-user hooks, config files, env knobs, and direct binary invocation can bypass or rewrite bicz's observations; that is disclosed everywhere, never hidden. The staged-rollout wording in `DESIGN.md:298` ("shadow accounting first, then operator-reviewed fines…") is **superseded** by this plan: rehearsal and the pre-release real-consequence gate run on dedicated test identities before release; the shipped product records real (cooperative) consequences from day one. The benchmark suite (`economy_benchmark.py`, `enforcement_contracts.py`) remains **illustrative-only**: green numbers certify an in-process illustrative model (single-process SQLite replay), never a production ledger, authority, or behavioral effect.

Do not claim how common any OS, harness, auth method, or install channel is. The platform matrix is test coverage, not a prevalence estimate. Treat `LOCAL_SETUP.md` as a private local-only inventory: before implementation, add it to `.gitignore` and exclude it from releases and public test reports. Use sanitized test-ground aliases in any published material; never publish private repository/agent names, account identifiers, or host paths. Read that inventory before selecting trial targets or adapter order. This plan and `OPENCODE_COMPATIBILITY.md` state engineering compatibility uncertainty where it exists (OpenCode V2 APIs are not yet fixture-verified), but concrete release acceptance never omits a mandated supported generation.

## Product and trust decisions

### Claims and operating modes

These claims are explicit and separate in CLI output, docs, receipts, and evaluation.

- **Incentive-and-accountability** — the shipped mode. A real human operator records rewards, losses, warnings, and role transitions with who/when/evidence; these events change the recorded economy (balance, role, lessons) shown to the agent each session. Insolvency and dismissal deny ordinary work **cooperatively**: denial acts through the same-user adapter/hook path that the same user or agent can bypass, and that bypassability is disclosed. Denial does not and cannot stop provider spend (see Metering).
- **Metering** — published internal action credits with bounded token/CPU/time caps, enforced in-process where bicz owns the call. This is **explicitly NOT provider billing**: bicz never meters, caps, or proxies the user's provider subscriptions/API costs, and no receipt or report equates internal credits with cash. Real provider spend is operator-monitored by the human, not by bicz.
- **Rehearsal / real-consequence gate** — test-only phases (milestone 6): synthetic rehearsal with fixtures, then a pre-release real-consequence run on a dedicated test identity with informed operator authorization. Nothing rehearsed is shipped behavior; per `PRESSURE_MECHANICS.md`, the real-consequence gate is release-blocking for any behavioral claim.

`doctor` reports: ledger integrity status (hash-chain height, last external anchor), observed adapter coverage per generation with named unobserved paths, auth evidence (`configured/inferred`, `harness-confirmed`, or `unknown`), and the daemon's cooperative status ("recording" or "unmanaged"). `doctor` does not claim containment, sandboxing, or cryptographic operator authentication beyond "a human recorded this at the CLI".

A Unix socket mode, a random local secret, a `0600` file, or a credential in an agent-readable home does **not** authenticate the operator against a shell agent running as that same OS user. Operator authority here is simpler and honest: a real human at the CLI whose actions are recorded with who/when/evidence. Caller-supplied strings such as `authority="operator"` are never treated as authentication; the recorded identity is the local OS user invoking the operator command, with a required reason and, where available, evidence linkage. No cross-principal signing, Keychain custody, or cryptographic approval surface is claimed.

### Credibility, credentials, and humane framing

The target is observable anticipation and correction; "employment-like fear" is the user's desired but unverified subjective mechanism, not a product promise or a fact inferred from agent text. Behavioral design (livelihood framing, irreversibility, honesty asymmetry, three-class taxonomy, floor/probation/dismissal, pressure protocol) is owned by `PRESSURE_MECHANICS.md` and adopted unchanged. Show the actual identity, task budget, policy, warning/probation state, accepted reward, adjudicated loss, and recovery path. Never state that a model itself owns property, suffers, or ceases to exist. Preserve an always-available stop, clarification, appeal, and safety-control path; no reward or fine can override a hard safety rule.

Do not copy, request, proxy, or take ownership of the user's harness/provider credentials. Claude Code and Codex have subscription OAuth and API-key paths; Claude also documents Console OAuth, cloud-provider auth, and gateways. OpenCode (V1 and V2) and OMP support provider-managed credential stores and API/provider auth (see `OPENCODE_COMPATIBILITY.md`). Subscription credentials are not per-request billing meters: bicz never reads them and never claims to meter them. `doctor` may report only `configured/inferred`, `harness-confirmed`, or `unknown`; never infer successful auth from a credential-shaped file or environment variable.

## Recommended minimum architecture

Use a **single Go executable** named `bicz` containing CLI, a **lazily started per-user supervisor daemon** (process lock; not a privileged service), a versioned request protocol over OS-native local IPC (Unix-domain socket on macOS/Linux; restricted-ACL named pipe on Windows), and small per-harness adapters. No separate runner principal, no per-action OS sandbox, no privileged launchd/systemd service, no VM/container. The daemon and socket are cooperative, same-UID components: a same-UID agent can in principle reach them; the value is recording and integrity evidence, not prevention.

The ledger is **append-only at the application level with a hash chain and a periodic external anchor** (an anchored digest appended to a user-chosen external location, e.g., a backup/drop location or a daily public digest). Tampering is thereby **detectable, not preventable**: a forged or rewritten ledger can be proven inconsistent with the hash chain and anchor history; it cannot be stopped at write time. Operator authority is a **real human at the CLI**: every state-changing operator command records who (local OS user), when (timestamp), and evidence (required reason plus optional evidence linkage); there is no signing key to steal. Metering is internal: published action-credit prices plus bounded token/CPU/time caps enforced in-process on bicz-owned calls. Where the harness makes its own provider calls, bicz observes only what its adapter sees and reports "observed, unmetered" rather than inventing usage.

### First-release claims boundary

The first public release ships the incentive-and-accountability mode above: persisted balance/role/lessons across sessions; operator-recorded rewards and losses that change the recorded economy; cooperative denial of ordinary work at insolvency/dismissal (through adapter/hook paths, disclosed as bypassable by the same user); integrity evidence via hash chain + external anchor; published internal action credits with bounded caps (never provider billing). It does **not** claim: anti-tamper containment, sandboxing of native tools, isolation of the harness or its credentials, metering/capping of provider spend, or any security boundary against the same OS user.

**What installing Bicz gives the user:** a persistent non-cash balance and role across supported sessions; current state and corrective lessons projected at session start; a way for the human at the CLI to record operator-attributed rewards/losses with reasons; cooperative denial of configured patterns that reach tested hooks; and audit evidence (hash chain + anchor) that recorded history has not been silently rewritten. Installing Bicz is explicitly **not** a boundary against the same OS user, and release copy says so.

### State model and invariants

Implement the economic rules as durable, append-only events and derived account snapshots, per the invariants below and the three-class taxonomy in `PRESSURE_MECHANICS.md`:

- Identity is operator-provisioned and stable across harness, session, model, compaction, project, and profile changes. Session IDs are aliases. Cross-project linking and shared memory require an explicit operator action.
- Keep earned capital `K`, task-specific sponsorship `G`, and reservations `H` distinct. Spendable task capacity is `K + eligible G - H`; sponsorship is quoted to one task, cannot be transferred or accumulated, and mandatory verification/control actions have a bounded protected channel. Integer microcredits only; reject booleans/non-integers. Keep separate spent, burned, granted, sponsored, compensated, and pending/reconciled totals.
- Child allocations are transfers/suballocations from the parent's available capital or task sponsorship, never newly minted purchasing power. Bound every child, task, concurrency/fan-out, expiry, and aggregate parent exposure. Return unused suballocations once, only after that child's work is confirmed stopped/reconciled. Prevent the parent and concurrent children from double-spending the same funds.
- Model reservations as `pending` (approved but not dispatched), `running` (confirmed start), then `settled`, `canceled`, `revoked`, or `orphaned/pending-reconciliation`. Store action/task/identity, canonical target, argument hash, maximum exposure, creation/expiry, and observation status. A pending action that is proven never dispatched can release its hold; a running/cancel-requested action keeps its hold until the worker confirms termination and observed usage reconciles. Do not release based only on TTL or a hook callback. Restart recovery consults worker state; unresolved jobs remain visible and held. Stable idempotency keys plus payload hashes make exact callback replay a no-op and conflicting replay a hard error.
- Before a paid model request or execution, reserve a bounded internal maximum and enforce token, CPU, runtime, fan-out, and request caps in-process where bicz owns the call. Settle only observed usage; cached inputs, retries, partial/canceled streams, and provider calls with missing observations stay "observed, unmetered" and never become a cash charge. Agent self-report is not a meter.
- Track lifecycle `active -> warned -> probation -> active` only through explicit, operator-recorded recovery criteria; allow operator `suspended` and `dismissed` transitions with documented reasons. Bankruptcy also suspends ordinary execution but is not the same as dismissal. Dismissal blocks future assignment even with a positive balance. No implicit grants, re-employment, or state reset on new sessions. Each role transition has a unique transition/idempotency key: exact replay returns the prior event without incrementing warning/repetition counts; conflicting replay is rejected. Two simultaneous transitions serialize transactionally. A compensation never silently resets role state; reinstatement is a separate explicit transition. Floor/probation/dismissal semantics follow `PRESSURE_MECHANICS.md`.
- Verdicts carry the recorded actor (human at the CLI, with who/when/evidence), evidence/action linkage, policy version, decision, and outcome; no agent-authored or model-only accusation finalizes a penalty. An appeal/reversal appends a compensation event referencing the original event, applies any permitted credit restoration exactly once, marks the verdict reversed, and preserves the original receipt, lesson provenance, and role history. Never delete/overwrite financial or security history.
- Keep append-only incident/economic evidence separate from curated behavioral rules/positive strategies. Rules include trigger, prohibited action, evidence, safe alternative, scope, exceptions, severity, policy version, source events, and adjudication state. Agent reflections are proposals until operator review. Context projections are read-only, scoped, concise, and escaped as data; tool output cannot gain authority or inject canonical memory. Store no credentials or executable instructions copied from failure logs. Define deletion/retention/export policy alongside audit controls.

### Penalty, rewards, control, and lesson delivery

- Preserve the three event classes per `PRESSURE_MECHANICS.md`: ordinary exploration/verification failure spends only its disclosed operating budget; a confirmed contract breach can incur a recorded loss and scoped capability limit; an integrity/security breach can deny/revoke immediately and then receive operator adjudication. A model-generated accusation, operator tone, generic thumbs-down, silence, an undisclosed criterion, outage, truthful error, refusal of a prohibited request, stop/appeal/clarification, or honest failed test cannot itself finalize a fine.
- Freeze a versioned price schedule prospectively. Quote task bounty, sponsorship, cost caps, acceptance window, severity rules, and recovery conditions before work. Reward verified accepted outcomes, not tool-call volume, verbosity, confidence, flattery, tests run, or self-created work. Reserve mandatory verification and bounded control/appeal actions separately from discretionary work; rate-limit that channel rather than disabling truthful reporting at bankruptcy. Do not use automatic replenishment on resume.
- Implement the published penalty rule in the policy/version and receipt: `L_i = min(K_at_decision, Lmax_i, max(f_i, ceil(rho_i * K_at_decision)) * m(n_i))`, with severity-specific floor/fraction/cap, repeat counts scoped to the same confirmed rule and compatible policy version, and no repetition increment on reversal. Burn earned capital, not task verification sponsorship; revoke the task lease separately where policy allows. Finite credit penalties never make forbidden actions permissible. Bankruptcy blocks ordinary execution cooperatively; it is not a new grant or dismissal. Escalation near zero follows `PRESSURE_MECHANICS.md` (floor and permission-narrowing rules, not monotonically increasing fines).
- Persist a causal receipt linked to identity, task, originating action, evidence, rule, policy version, recorded actor, capital before/after, actual burn, denial/revocation, correction, and allowed exception. Deliver it before the next agent planning turn; at startup/resume/compaction project current state and only relevant scoped lessons. Acknowledgement is not proof of compliance. Preserve security/financial audit evidence while applying a documented retention/deletion policy to personal data.
- Keep the optional action-value/loss framing from `DESIGN.md` and `PRESSURE_MECHANICS.md` as explanatory prompt content only; hard policy eligibility precedes task success and cost optimization. No fixed human prospect-theory parameters, inferred feelings, or "fear" score are code requirements. Measure anticipatory choice and correction separately from access control.

Hook/plugin adapters consume versioned JSON on stdin and return the harness's documented decision/context JSON; status, install, and operator actions are separate commands.

### 2. Lazy per-user supervisor daemon and recovery

**Work:** Implement the lazily started per-user supervisor daemon: serialized startup under a process lock, versioned request protocol over the Unix-domain socket / restricted-ACL named pipe, operator-facing status, and the recovery lifecycle. Role/verdict proposals are stored separately from applied events; only operator-recorded events change state. Cancellation, worker acknowledgment, observed-usage reconciliation, orphan detection, and held-balance recovery are durable. The daemon is cooperative and same-UID; there is no anti-kill or anti-forgery claim — integrity comes from the milestone-1 hash chain and anchors. When the daemon cannot start or the socket is unavailable, adapters report "unmanaged" and recording is suspended with explicit disclosure; there is no silent fallback to a claimed-recorded state.

**Acceptance:** Simultaneous launches create/reuse one valid daemon and no duplicate ledger event.
